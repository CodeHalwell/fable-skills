# Deployment Strategies

## The standard doctrine, compressed

A strong model already produces this cold; one line each so the corrections below have anchors. Deploy ≠ release — flags/canaries/dark launches decouple the risky event from the observable one. Score every plan on blast radius × detection time × reversal time; optimize MTTR, not zero-failure. The database is the hard part (ask "and what about the data?" first); expand → dual-write → backfill (batched, idempotent, key-range, lag-throttled) → migrate reads → contract-last-and-alone; N and N−1 must both work against the current world state at every moment, including queues (consumer deploys before producer) and caches. Rolling for low stakes; blue/green for instant total reversal (worst blast radius, best reversal; compute-only isolation — the shared DB still needs expand/contract; drain long-lived connections); canary for blast-radius control, needing per-version metrics and enough traffic for signal (1% of 100 rps is statistically useless — use one-instance staged rollout or cohort canary instead). Canary judged against a *concurrent baseline control* (fresh pods of the old version), never last week. Rollback-first under pressure; fix-forward only when rollback is genuinely impossible. Config changes are deploys: version, review, validate shape/size, stage region-by-region, one-command revert. Postgres indexes: `CONCURRENTLY`, which requires leaving the migration transaction (`disable_ddl_transaction!` in Rails, `atomic = False` + `AddIndexConcurrently` in Django), and cleanup of INVALID indexes on failure.

## Corrections and sharpenings

- **The 2025–26 config-outage record, precisely.** Cloudflare Nov 18, 2025 (DB permission change doubled a bot-management config file past a consumer's hard size limit, global proxy panic) and Azure Front Door Oct 29, 2025 are widely known. Less known: **Cloudflare had a second outage Dec 5, 2025** — a *global config kill-switch flip* hit a latent proxy bug; the mechanism to know is that even a "safety" config path (the kill switch itself) is a config deploy with global blast radius and must be staged and rehearsed like any other. The pair makes the argument complete: config artifacts need generation-time shape/size validation *and* staged propagation *and* exercised revert paths — a validated file that propagates globally in one shot still fails globally.
- **A canary can't see aggregate failure modes — canary the *load*, not the request percentage.** The reflex fix ("run the canary longer") doesn't help: connection-pool exhaustion, cache stampedes, and dependency rate limits scale with total load, so 1% passes and 100% detonates. Canary by cell/region so one unit carries production-shaped load, and watch the *shared dependency's* saturation metrics, not the canary's error rate.
- **The deploy-window debate resolves through MTTR, in that order.** "Never deploy Friday" vs "deploy anytime" is not a culture question: your allowed window is a function of rehearsed reversal time. If rollback is one command anyone on-call can run and detection is automatic, Friday 4pm is fine; if rollback needs the one engineer who understands the migration, Tuesday 10am is the only responsible window. Fix the MTTR, *then* relax the window — teams that relax the window first are gambling, and teams that impose freezes instead batch up changes and make the first post-freeze deploy the year's riskiest (a freeze without a fast-track exception path just produces undocumented hotfixes).
- **Automated canary judges fail by metric count.** A judge watching 40 metrics fails healthy canaries constantly (multiple comparisons), gets turned off, and then nothing gates promotion — worse than no judge. Keep the gated set small: error rate, p95/p99 latency, 1–3 domain metrics that catch *silently wrong* results (orders/min, login success), plus memory slope for leaks. Soak per step must cover the slowest feedback loop you care about (cache TTL expiry, hourly crons, leak slope) — a 5-minute pause catches crashes, not leaks.
- **"Fix forward, rollback loses today's data" — interrogate it.** Usually only the *schema* moved forward and code rollback is fine against the expanded schema; people conflate "roll back the code" with "restore the database." The whole point of expand/contract is that you almost never need the latter. (And "restore the backup" is not a rollback strategy — it's data loss for everything written since.)
- **Version cache keys so rollback misses instead of exploding:** `user:v2:{id}` — new code populates v2; rolled-back code reads its own v1 keys and eats a cache-miss penalty rather than deserialization crashes. Delete v1 population in a later deploy (it's a contract step).
- **Flags are debt with a deletion date, and three species.** Release flags: owner + removal ticket *at creation*, dead within weeks of 100%. Ops kill-switches: long-lived and *tested on a schedule* — an unexercised kill switch is a rumor (the "off" path was broken by a refactor months ago, discovered the day you need it). Entitlement flags: not flags — move them to product configuration. Ten stale flags = 2^10 config states nobody has run together. Flags gate *availability*, never authorization — an endpoint checking only the flag turns flag misconfiguration into free features or data exposure. Bucketing sticky by user-ID hash or your metrics are garbage; flag flips are config deploys (audit log, staged, "flipped to 100% at 4:55pm Friday" is a classic incident opener).
- **Silent-wrongness rollouts invert the risk locus.** For a change whose failure mode produces no errors (pricing, ranking, billing): shadow mode — compute both, serve old, log disagreements with inputs, in *production* (staging lacks the weird carts/coupons/currencies where the bugs live). Only after mismatches converge to a known accepted set do you flip serving via flag, watching business metrics against control. The code deploy itself becomes non-risky (plain rolling) because the *flag flip* carries the risk and reverses in seconds — that inversion is the design. Then delete the old path on a scheduled ticket; keeping both "just in case" means every future change is implemented twice.

## Verification / self-check

1. During rollout, both versions run concurrently — name the specific mixed-version interaction you checked (DB, queues, caches).
2. What is the *rehearsed* undo action, who can run it, how long does it take? ("Revert the PR and wait for CI" is a 45-minute answer pretending to be one.) Rehearse a rollback on a healthy deploy quarterly and time it.
3. Which metric is split by version and would catch a silently wrong result, not just errors?
4. Name each one-way door (dropped column, new-format messages, client-visible API change — clients can never be rolled back; flag server-side instead). Each goes in its own late-stage deploy.
5. Every new flag has an owner and a removal ticket; every contract migration is scheduled, not hoped for. Until cleanup ships you're still mid-deploy.
