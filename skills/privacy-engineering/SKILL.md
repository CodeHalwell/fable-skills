# Privacy Engineering

## The standard doctrine, compressed

A strong model already produces this cold; anchors only. Minimization is the master principle (don't collect → don't retain → aggregate/pseudonymize → restrict+encrypt); personal data is a liability with interest. You can't protect what you can't find — the data map is the load-bearing artifact, and the mass is in shadow copies: logs, backups/versioned buckets, warehouse time-travel/replicas, caches, search and vector indexes, queues/DLQs and sink connectors, error trackers, session replay, support tooling and Slack screenshots, prod-seeded staging, ML artifacts, third-party SDKs collecting on their own account. `sha256(email)` is pseudonymization, not anonymization (enumerable input, universal join key — still personal data under GDPR; industry hashed-email matching is linkage by design). K-anonymity: homogeneity/composition attacks, unusable on high-dimensional data. DP is the only real guarantee — aggregate releases only, vetted libs (OpenDP, PipelineDP, Opacus), and it's theater without cumulative budget accounting and correct sensitivity. Deletion: orchestrated fan-out with per-store registration and retries; keyed-hash tombstones re-applied on every restore; backups age out on a bounded schedule or crypto-erasure via per-user/tenant keys (the only tractable story for immutable stores, WORM, warehouse time-travel); deletion events on the same bus with retention shorter than the deletion SLA. DSAR exporter = the deletion fan-out in read mode — build both on one registry. 72-hour breach clock = pre-built access logging on PII stores + a rehearsed "what did principal P touch in window W" query, or you over-notify for the worst case. Log scrubbing: allowlist structured logging as the control, scanner as the alarm — denylist regex always loses. Session replay: events-first; if replay, mask-by-default/unmask-allowlist, client-side before upload, payment fields never. Embeddings are invertible-enough to classify at (near) source-text tier; RAG deletion must reach chunks/embeddings and retrieval must enforce source ACLs. Machine unlearning is not production-ready (2026): honest answer = exclude from future training + retrain/deprecate on schedule + model retention policy; minimize memorization up front (dedupe, canaries, DP-SGD where affordable). Encryption-at-rest answers exactly one question (stolen media); field-level/KMS envelope crypto is what changes the threat model, and the IAM-audited decrypt trail is half its value.

## Corrections and sharpenings

- **EU AI Act status (as of mid-2026) — the part the baseline hedges on:** prohibited-practices (Feb 2025) and GPAI obligations (Aug 2025) are in force; the high-risk Annex-III obligations were scheduled for Aug 2026, **but the "Digital Omnibus" package agreement defers some high-risk deadlines to late 2027** — a model answering from training data will tell you "the Aug 2026 date stands unless amended"; it was amended. Treat exact dates as counsel's input; the engineering posture is settled regardless: classify systems against high-risk categories, keep technical documentation, data-governance records, human-oversight mechanisms; DPIA and AI-Act risk assessment overlap but are distinct. US states: 150+ AI laws enacted and climbing (Colorado's effective date itself slipped) — build to the strictest common denominator, not per-state toggles.
- **Consent is checked in the serving path, not at collection.** The recurring implementation gap: the opt-out flag lives in the users table while the analytics SDK fires unconditionally, or the "don't train on my inputs" flag isn't read by the training-corpus builder — an unenforced opt-out is a contract breach *at training time*. Every consent basis needs a named code location where it gates processing, and a test proving flag-off → event-absent. Reuse of existing data for a new purpose is a design-review event, never just a query.
- **Make the map executable.** Schema annotations tooling can enforce (protobuf field options, dbt column meta, BigQuery policy tags) with a CI rule like "no tier-direct column flows to the default analytics dataset" beat any spreadsheet inventory. Most counsel-vs-engineering fights dissolve into "we didn't know that store existed" — the map is the shared ground truth.
- **Retention is enforced in the same PR that creates the data** (S3 lifecycle incl. `noncurrent_version_expiration` — versioned buckets retain "deleted" bytes; partition expiration; pg_cron), or it doesn't exist. Five years later the "30-day" logs are 400 TB of unknown liability.
- **Derived stores resurrect people.** The nightly-upsert feature table keeps deleted users' last-known values forever; ETL re-materializes from un-tombstoned sources; restores un-delete. Deleters must be *registered per store to pass design review*; a quarterly synthetic-user drill (create user → exercise everything incl. support ticket, analytics, an LLM prompt → delete → wait SLA → grep every mapped store *and the logs* for the identifiers) is the only falsifiable test — any hit means the data map was fiction.
- **LLM prompt/completion logs are the newest shadow copy of record.** Short default TTL (days–weeks), redaction before the eval/analytics tier (contractors read eval sets), training-opt-out enforced in the corpus builder with per-run lineage ("was user U in run R?"), zero-data-retention/in-region vendor modes on for enterprise tiers — now a standard procurement demand; know whether yours is enabled.
- **Residency is per-tenant routing, not a region checkbox.** The primary DB in eu-west-1 is void if the warehouse, LLM API, error tracker, and support tooling replicate to the US. Model residency as a tenant attribute consulted by storage routing, queue topology, and vendor selection; legal instruments only work if the architecture can make true statements about flows.
- **Aggregation hygiene even without DP:** suppress small cells (k≥10 for published counts) and watch *differencing* — this week's total minus last week's isolates individuals even when both pass the threshold.

## Worked spine

*PM wants session replay on checkout:* the decision is "which step loses users and why" — funnel + rage-click/error events answer 80% at 2% of the liability; push that first. If replay is truly needed: checkout pages only; allowlist masking (denylist fails on the renamed custom component); verify the vendor masks *client-side before upload* (post-ingest masking = you already shipped PII — the exact mistake in the public replay scandals); vendor = processor with DPA, in the data map, 30-day retention, deletion API wired into the fan-out, capture gated on the consent flag. Ship condition: a canary test asserting a fake card number typed into checkout never appears in a captured payload — falsifiable, not a policy sentence. Rejected: "keep recordings 1 year for trends" — the purpose was *this funnel*; trends come from the aggregate events. That is purpose limitation in practice.

## Verification / self-check

1. Collection: what decision does each new field drive? (Reject "might be useful.")
2. Mapping: every new store/vendor in the map with tier, purpose, owner, DPA + deletion API.
3. Retention: TTL enforced by which platform mechanism, visible in this PR.
4. Deletion & DSAR: deleter registered; exporter covers it; end-to-end SLA vs the 30/45-day clocks.
5. Consent: which basis, where checked in code, what test proves opt-out.
6. Exposure: who reads it (humans + services), IAM-audited; top-tier fields field-level encrypted; logs/analytics/LLM-prompts clean.
7. Claims audit: anything saying "anonymized" proves the adversary model or gets renamed "pseudonymized."
Run the synthetic-user deletion drill quarterly. Stopping rule: minimized collection + executable map + enforced TTLs + drill-tested fan-out + consent-in-code + field-level crypto on top tier = defensible; further effort goes to the newest shadow copies (latest pipeline, newest vendor, LLM logs) — posture decays by accretion.
