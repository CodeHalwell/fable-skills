# Model Serving Infrastructure

## Core mental model

- **You buy GPU-time; you sell tokens (or predictions). Utilization is the exchange rate.** A GPU bills per second whether it is saturated or idle. Every architecture decision — batching, autoscaling, fractional sharing, serverless — is a different strategy for closing the gap between GPU-seconds paid and GPU-seconds doing useful work. Reason about every serving proposal by asking "what does this do to sustained utilization?" before anything else.
- **LLM inference has two phases with opposite bottlenecks.** Prefill (processing the prompt) is compute-bound and parallel — an H100-class GPU chews through prompt tokens at tens of thousands per second. Decode (generating output) is memory-bandwidth-bound and sequential — hundreds of tokens/second aggregate, and only batching many concurrent requests recovers throughput. This asymmetry explains continuous batching, chunked prefill, prefix caching, prefill/decode disaggregation, and why input tokens are cheap and output tokens are expensive. When something about LLM serving seems weird, map it back to this asymmetry.
- **Latency and utilization are the same knob viewed from opposite sides.** Bigger batches raise throughput per GPU and raise per-request latency (inter-token latency degrades as batch grows; queueing delays TTFT). There is no setting that maximizes both. The expert move is to define the SLO first (e.g., p95 TTFT < 800ms, p95 inter-token < 60ms), then push batch size until the SLO is at the edge — utilization beyond that point is bought with SLO violations. "Goodput" (throughput of requests meeting SLO) is the metric, not raw tokens/sec.
- **Cold start is the tax on scale-to-zero.** Serverless pricing looks magical until the first request after idle pays 10–120s to pull an image and load 10–140GB of weights. Every cold-start mitigation (snapshotting, weight streaming, warm pools) is spending money or engineering to shrink that tax. Decide scale-to-zero per endpoint by comparing the tax rate (cold starts/day × latency cost) to the idle burn saved.
- **Generation is expensive and non-idempotent by default; retries multiply cost.** A retried 5-cent LLM call is not a retried 0.1ms Redis GET. Every retry policy, timeout, and load-balancer default inherited from web-service practice needs re-examination when a single request costs cents and runs for minutes.

## Decision framework: managed API vs serverless GPU vs dedicated

Ask these in order; each answer prunes the tree.

1. **Are the weights custom (fine-tune, proprietary model), or commodity open weights?** Commodity open weights → default to a managed per-token API (Fireworks, Together, and cloud-hosted equivalents, all alive and price-competitive as of 2026). They run at higher utilization than you ever will and pass some of it back. As of mid-2026, Llama-3.3-70B-class inference is ~$0.90/M tokens on these providers — self-hosting rarely beats that on raw price (see worked example). Only leave managed for: custom weights they won't host cheaply, data-residency/compliance, latency SLOs they can't sign, or token volumes where the arithmetic flips.
2. **If custom weights: what's the traffic shape?** Compute the duty cycle: busy GPU-seconds ÷ wall-clock seconds over a week. Spiky/diurnal with long idle valleys (<~40–50% duty cycle) → serverless GPU (Modal, RunPod, Baseten, Replicate — the latter Cloudflare-owned since early 2026, still operating). Sustained high duty cycle → dedicated GPUs (reserved instances are 30–40% below on-demand). Serverless per-second rates carry roughly a 1.5–3× premium over the same GPU on-demand (ballpark as of 2026); premium × duty cycle vs 1.0 × always-on is the whole comparison.
3. **If serverless: can you tolerate its cold start for THIS model size?** As of 2026: sub-second cold starts are real only for small containers (RunPod FlashBoot claims sub-200ms for a large share of requests, small images). Large-model cold starts: Modal's GPU memory snapshotting brought a vLLM 7B-class server from ~2 minutes to ~10s (single-digit seconds best case); Baseten-style platforms still see 30–90s for big model containers after scale-down. If the product cannot ever show a 30s stall, you need a warm floor (min replicas ≥ 1) — which erodes the serverless cost story; recompute step 2 with that floor.
4. **If dedicated: does one node hold the model?** Fits on one GPU → plain vLLM behind a standard load balancer; don't add orchestration you don't need. Fits on one node with tensor parallelism → vLLM with TP, still simple. Needs multi-node, disaggregated prefill/decode, or KV-cache-aware routing at fleet scale → the 2026 distributed layer: llm-d or KServe on Kubernetes (NVIDIA GPU Operator underneath), NVIDIA Dynamo (1.0 GA as of March 2026) for disaggregated serving, Ray Serve when multiplexing many models per cluster. Adopt these for a measured reason (routing losses, cache-hit rates, cross-node models) — not because they're the modern stack.
5. **What would change the answer?** Traffic 5×'ing (serverless premium starts to dominate), the managed provider deprecating your model, a new fine-tune requirement, or per-token prices moving (they fall steadily; re-run the break-even quarterly, and mark any cached calculation with its date).

## GPU utilization economics

- **Batch to saturate decode.** A single-request decode uses a few percent of an H100's capability. Continuous batching (vLLM default) is what turns 20 tok/s into hundreds aggregate. If per-GPU throughput is far below published benchmarks for your model class, the cause is almost always insufficient concurrency, `max_num_seqs` too low, or KV-cache memory exhausted by long contexts — not the engine.
- **Right-size the GPU to the model, then fill the leftover.** A 7B model at FP8 uses ~8GB of an 80GB GPU for weights; the rest is KV cache (good — more batch) or waste (bad — you bought an H100 to serve traffic an L4 could hold). For small models, several cheap GPUs beat one big one on $/token.
- **Fractional GPUs (as of 2026):** MIG (Ampere and later) partitions one GPU into up to 7 hardware-isolated instances with dedicated compute/memory — use for co-locating small latency-sensitive models where noisy neighbors are unacceptable. Time-slicing shares without isolation — fine for dev/bursty batch, never for latency SLOs (one tenant's long kernel stalls everyone). MPS sits between (concurrent kernels, no memory isolation). On Kubernetes, allocation is moving from the static device plugin to DRA (Dynamic Resource Allocation) — NVIDIA's DRA driver was donated to CNCF in 2026 and is the direction of travel, but note MIG shapes still require static pre-configuration; DRA does not yet re-partition dynamically (as of mid-2026). Practical consequence: choose MIG geometry per node pool ahead of time and label pools by shape.
- **Fractional GPUs are irrelevant for big LLMs.** A model that fills the GPU can't share it. Fractionalization is for the long tail: embedders, rerankers, small classifiers, ASR — where it routinely triples effective utilization.

## Autoscaling for inference

- **Scale on work waiting, never on CPU or GPU "utilization %".** CPU is idle on a GPU server; nvidia-smi GPU-util reads high even when the GPU is memory-stalled at low throughput — both signals lie. Correct signals, in preference order: queue depth (requests admitted but not started), in-flight concurrent requests per replica vs a measured max, and KV-cache utilization for LLM servers. KServe/Knative-style concurrency-per-replica targets and KEDA on queue length are the standard mechanisms; vLLM exposes queue and cache metrics via Prometheus (`vllm:num_requests_waiting`, KV-cache usage gauges) — wire the autoscaler to those.
- **Set the scale-up threshold from the cold-start time, not from taste.** If a new replica takes 90s to serve traffic, you must scale when the queue *predicts* saturation 90s out. If traffic can spike faster than replicas boot, no threshold saves you — you need a warm pool or overprovisioned headroom (~20–30% is typical for spiky LLM traffic).
- **Cold-start mitigation ladder** (cheapest first): (1) bake weights into the image or a pre-warmed volume — never download from a remote hub at boot; (2) stream weights from region-local object storage with a loader that overlaps download and GPU load (safetensors + parallel range reads; managed platforms do this for you); (3) snapshot/restore of initialized GPU state (Modal's GPU memory snapshotting class of technique, as of 2026); (4) warm pools — booted, weights-loaded replicas held out of rotation; you pay idle for insurance, size the pool to spike statistics, not worst case ever.
- **Scale-to-zero is a product decision.** Zero replicas means the next user waits 10–90s. Right for internal tools, batch endpoints, and long-tail models; wrong for anything interactive with steady daytime traffic. The compromise is floor-1 during business hours, zero overnight — a cron-shaped `minReplicas` schedule, embarrassingly effective.

## Streaming APIs done right

- **Use SSE (`text/event-stream`) for token streaming; it's the ecosystem convention** (OpenAI-compatible APIs, vLLM's server). Send an event per chunk, a terminal `data: [DONE]` sentinel, and heartbeat comments (`: ping`) every ~15s so idle prefill periods don't trip proxy idle timeouts. Disable proxy buffering explicitly (`X-Accel-Buffering: no` for nginx; check every hop — one buffering ALB/CDN layer turns your stream into a single blob at the end and users see nothing until completion).
- **Timeout per gap, not per request.** A 4k-token generation legitimately runs minutes. Set (a) a TTFT timeout (~30–60s — if nothing arrived, the request is queued/stuck; safe to act), and (b) an inter-chunk timeout (~10–30s — the stream died). A single whole-request timeout either kills legitimate long generations or lets zombies run forever.
- **Retries must be idempotent or they double your bill.** Naive client retry on timeout while the server is still generating = two GPUs computing the same answer, and with at-least-once queues, possibly two answers delivered. Require client-supplied idempotency keys; on retry, reattach to the in-flight generation (or replay from a result cache) instead of restarting. Only auto-retry errors that provably occurred before generation started (connect failures, 429/503 at admission). Never auto-retry mid-stream failures at the infra layer — surface them and let the client decide with the partial output in hand.
- **Backpressure: the GPU produces tokens whether or not the client reads them.** A slow client on an unbounded server-side buffer accumulates memory; worse, a *disconnected* client whose request keeps generating burns GPU for no one. Propagate client disconnect to the engine as an abort (vLLM supports request abort; verify your HTTP layer actually forwards cancellation — many async frameworks silently don't). Cap per-connection send buffers and drop-or-abort on sustained non-consumption.

## Multi-model serving

- **Route at a gateway, multiplex on shared GPUs only for small models.** One process per big model; a router (OpenAI-compatible gateway pattern) maps `model` field → backend pool. Co-locating two big LLMs on one GPU halves each one's KV cache and couples their failure modes — don't, unless both are small and MIG-isolated.
- **Multi-LoRA is the exception that changes the economics.** Dozens-to-hundreds of fine-tunes sharing one base model can be served from a single engine: base weights loaded once, per-request adapter selection, adapter-aware batching. vLLM has native multi-LoRA (`--enable-lora`, per-request `model=<adapter>`), and LoRAX established the pattern; adapter hot-load from local disk is milliseconds-to-subsecond for low ranks (as of 2026). Costs: small per-token latency overhead, adapters must share the exact base (same version, same tokenizer), and adapter cache thrash if the working set of adapters exceeds GPU headroom. If you're fine-tuning per customer, design for LoRA-on-shared-base from day one — full-weights-per-customer is a 10–100× infra cost mistake.
- **Fleet-scale routing (as of 2026):** KV-cache-aware routing — send a request to the replica already holding its prefix (same session, same system prompt) — is now productized in llm-d, NVIDIA Dynamo, and AIBrix. It matters when prefixes are long and reuse is high (agents, chat with big system prompts): a routed cache hit skips most of prefill. Below fleet scale, get 80% of the value with session-sticky routing (hash session ID → replica) plus vLLM's automatic prefix caching within each replica.

## Versioning and rollout for models

- **Immutable versions, pinned deploys, no "latest".** A model version = weights hash + engine version + sampling defaults + prompt template. Engine upgrades are model changes: the same weights on a new engine version can change outputs — canary engine bumps like model bumps.
- **Rollout ladder: offline eval gate → shadow → canary → progressive.** The eval gate (fixed golden set + LLM-judged or task-metric comparison vs incumbent) is what makes automated rollout safe; without it you're shipping vibes. Shadow (duplicate real traffic, log candidate outputs, act on nothing) validates latency, OOM behavior, and output-distribution sanity under real prompts — it cannot measure user impact. Canary by *user/session*, not by request: per-request assignment gives one user alternating model personalities mid-conversation and contaminates measurement.
- **Keep N and N−1 warm during rollout.** Rollback for a model is not a config flip if the old weights take 5 minutes to load; hold the incumbent's replicas until the canary clears its bake window.

## Observability specifics

Instrument these or fly blind (all exposed by vLLM-class servers via Prometheus):
- **TTFT** (p50/p95/p99) — queueing + prefill; the first metric users feel. Rising TTFT with flat traffic = growing queue = you're saturated.
- **Inter-token latency / output tokens-sec per request** — decode health; degrades as batch grows; this is your SLO-vs-utilization dial readout.
- **Queue depth and requests-waiting** — the autoscaling signal and earliest saturation alarm.
- **KV-cache utilization and preemption/eviction counts** — cache at ~100% with preemptions means requests are being paused/recomputed; throughput falls off a cliff *before* OOM. Alert at ~90%.
- **Prefix-cache hit rate** — a regression here (after a prompt-template change that broke prefix stability, e.g. a timestamp inserted at the top of the system prompt) silently doubles prefill cost.
- **Tokens in/out per request distributions** — shape changes are cost changes; a p99 input-length jump predicts OOM and head-of-line incidents.
- **Quality drift**: sample production outputs continuously into an eval pipeline (judge model or task metric) per model version. Serving metrics can be pristine while a bad rollout, quantization change, or prompt regression tanks quality — output-quality sampling is the only detector.

## How an expert thinks through this

Scenario: a team fine-tuned an 8B model for support-ticket drafting. Traffic: ~40k requests/day, 9-to-5 diurnal, near-zero nights/weekends. Each request ~1,500 tokens in / 300 out. They ask for "a Kubernetes GPU cluster with KServe, llm-d, and autoscaling."

- First question: is the requested stack proportionate? 40k req/day peaks at maybe 2–3 req/s. An 8B model at FP8 on one L40S/A100-class GPU with continuous batching handles that with room to spare. So this is a 1–3 GPU problem, not a platform problem. *Reject the k8s+llm-d buildout*: llm-d/Dynamo-class disaggregation earns its complexity at fleet scale with long shared prefixes; here it's months of platform work to serve 3 req/s.
- Can they just use a managed API? No — custom fine-tune, and the ticket data has residency constraints. Managed per-token is out; note it would have been ~$65/day at 2026 open-model prices, a useful cost ceiling to beat.
- Traffic shape: ~10 busy hours out of 24, weekends off → duty cycle ~30%. That's the serverless zone. *Consider dedicated anyway*: one on-demand A100/L40S at ~$1–2/hr is ~$30–50/day always-on — actually cheap enough that the decision isn't purely cost. What breaks the tie: ops burden and the second GPU. Peak needs burst to 2 replicas; owning a second always-on GPU for 2 hours of daily peak is pure waste. Serverless with min=1 during business hours, scale to 2–3 on queue depth, zero on weekends captures that.
- Cold start check: 8B FP8 ≈ 9GB of weights. On a platform with weight caching/snapshotting, cold start is ~5–15s (as of 2026). Weekend scale-to-zero means Monday's first user waits ~10s — acceptable for an internal drafting tool. *Reject scale-to-zero overnight on weekdays*: a 7am early user hitting a cold start every single morning is a daily papercut; schedule the floor to 1 at 7am instead.
- Streaming: drafts are read as they generate, so SSE with disconnect-abort — agents close tickets mid-generation constantly, and without abort propagation ~10–20% of GPU time would be spent generating into closed sockets.
- Rollout: they retrain monthly. Wire the eval gate now (golden set of 200 tickets, judged against incumbent), shadow the new adapter for a day, then canary by agent-ID. *Reject shadow-only promotion*: shadow can't see that agents edit the new model's drafts twice as much — that needs the canary plus an edit-distance metric.
- Stopping rule: one serverless endpoint, scheduled floor, queue-depth autoscaling, SSE with aborts, eval-gated monthly rollout. No k8s, no MIG, no router. Revisit only when traffic 10×'s or a second model appears.

## Failure modes & pitfalls

- **OOM on long context, weeks after launch.** The server was tuned with `--gpu-memory-utilization 0.9` and typical 2k-token prompts; one day a user pastes a 100k-token document and the request either OOMs the engine or (vLLM) forces mass preemption that craters everyone's latency. Corrections: set `--max-model-len` to what you actually support, not the model's maximum; validate and reject/truncate over-limit inputs at the gateway; load-test at max context × max batch, not at typical values. Watch preemption counters — preemption storms precede OOM.
- **Autoscaling on GPU utilization %.** `DCGM_FI_DEV_GPU_UTIL` reads 95% whenever kernels are resident, including memory-stalled low-throughput decode — so the autoscaler thinks saturated-at-low-load and never scales *down*, or worse, the CPU-based HPA default never scales *up*. Correction: HPA/KEDA on `vllm:num_requests_waiting` or concurrent in-flight requests per replica.
- **Thundering herd on scale-up.** Queue builds → autoscaler adds 4 replicas → all 4 pull the same 30GB image and weights through the same registry/NFS path → 15-minute boot instead of 2 → queue grows → autoscaler adds more. Corrections: region-local weight cache or pre-baked images; jittered/staggered replica starts; cap scale-up step size; alarm on "replicas requested vs replicas Ready" divergence.
- **Head-of-line blocking by long prompts.** Without chunked prefill, one 80k-token prefill monopolizes the GPU for seconds while every in-flight decode stalls — users see mid-stream freezes. Corrections: enable chunked prefill (default in vLLM's V1 engine, as of 2026 — verify on your version); cap `max-num-batched-tokens`; segregate a long-context pool behind the router so whale requests can't sit in the interactive pool's queue.
- **Retry amplification.** Gateway timeout at 60s, generation takes 90s: gateway retries, now two GPUs generate; client library retries too, now four. The bill quadruples and p99 worsens because retries deepen the queue. Corrections: idempotency keys with in-flight deduplication at the gateway; retries only on pre-admission failures; retry budgets (max ~10% of traffic may be retries — a circuit breaker, not a policy suggestion).
- **A proxy that buffers SSE.** Everything works locally; in staging behind the corporate ALB/nginx/CDN, tokens arrive as one lump after 40s. Correction: `X-Accel-Buffering: no`, `proxy_buffering off`, disable response buffering/compression for `text/event-stream` on every hop; test streaming through the full production path, not localhost.
- **Client disconnects don't cancel generation.** Async HTTP frameworks often keep the handler running after the socket closes; the engine generates the full completion for nobody. At agentic/chat abandonment rates this is 10–30% of GPU spend. Correction: verify disconnect → engine abort end-to-end (kill a client mid-stream, watch running-request count drop within seconds).
- **Prefix cache as a cross-tenant side channel / correctness hazard.** Shared automatic prefix caching means one tenant's cached prefix can speed up (and via timing, leak the existence of) another's identical prefix; naive custom caches have returned wrong-tenant KV state outright. Correction: per-tenant cache salting (vLLM supports a `cache_salt` request field, as of 2026) or per-tenant pools when isolation matters.
- **Breaking prefix stability with a "harmless" prompt change.** Someone prepends `Current time: 09:41:07` to the system prompt; every request's prefix is now unique, prefix-cache hit rate falls to ~0, prefill cost doubles, TTFT jumps, and nobody connects the dots for a week. Correction: put volatile content at the *end* of the prompt; monitor prefix-cache hit rate and alert on step changes.
- **The MIG shape trap.** MIG partitions are chosen per GPU ahead of time from fixed geometries; a node pre-carved into 7 small slices cannot serve the new 13B model without draining and re-partitioning the node (dynamic MIG reconfiguration is still not handled by the DRA driver, as of mid-2026). Correction: separate node pools per MIG geometry; keep some whole-GPU nodes; treat re-partitioning as a node-lifecycle operation.
- **Judging cost by output tokens only, or by list price only.** Self-host vs API comparisons fail in both directions: forgetting that APIs charge for input tokens (input-heavy workloads favor self-hosting far more than output-token math suggests), and forgetting that your dedicated GPUs run at 30% utilization while the provider's run at 70%+ (favoring the API). Do the arithmetic with your real request shape and measured duty cycle — see the worked example.
- **Shadow-mode conclusions about quality.** Shadow traffic validates latency/stability and output *distributions*; it cannot tell you users prefer the new model, because nothing acted on its outputs. Promoting on "shadow looked fine" skips the only measurement that matters.
- **max_tokens left at a huge default.** Runaway generations (repetition loops) run to the 8k cap, holding batch slots and KV memory for minutes. Correction: per-endpoint `max_tokens` matched to the product (a ticket draft never needs 8k), plus repetition penalties or stop sequences; alert on p99 output length.

## Worked micro-examples

**1. Break-even: managed API vs dedicated H100 (2026 ballparks — recheck prices before relying on this).**
Workload: 70B-class model, requests of 2,000 tokens in / 400 out.
- Managed API: ~$0.90/M tokens (Llama-3.3-70B-class on Fireworks/Together, mid-2026, flat in/out). Per request: 2,400 tok × $0.90/M ≈ **$0.00216**.
- Dedicated: H100 SXM at ~$2.50/hr (specialized clouds ran ~$2.0–3.3/hr on-demand in 2026; hyperscalers 2–5× that) = $0.000694/GPU-s. Saturated per-GPU throughput for 70B at FP8: ~450–500 output tok/s aggregate at high batch, prefill ~15k tok/s (published 2026-era benchmarks; verify for your engine/quantization). GPU-time per request at saturation ≈ 400/460 + 2,000/15,000 ≈ 1.0 GPU-s → **$0.00069 at 100% utilization**.
- Break-even utilization = 0.00069 / 0.00216 ≈ **32%**. Below ~32% sustained duty cycle, the API is cheaper; above, self-hosting wins — and at 100% it's ~3× cheaper. One saturated H100 ≈ 86k such requests/day (~207M tokens/day); the break-even is ~28k req/day (~66M tokens/day) on this shape. Sensitivity: output-heavy shapes push break-even *up* (decode dominates GPU time while the API bills all tokens equally); reserved pricing (−30–40%) pushes it down; high prefix-cache hit rates push it down further. If your traffic is one region, diurnal, uncached, you will not sustain 32% without scale-to-zero — which is exactly the serverless pitch.

**2. Serverless vs always-on, same GPU.** Serverless H100-class at ~1.5–3× the on-demand per-second rate (2026 ballpark; take 2× = $5/hr-equivalent vs $2.50/hr dedicated). Serverless cost = $5 × busy-hours; dedicated = $2.50 × 24. Break-even busy time = 2.50 × 24 / 5 = 12h/day at the 2× premium (8h/day at 3×). A 9-to-5 workload (~8–10 busy hours) sits right at the line — which is why the scheduled-floor hybrid (dedicated-priced floor + serverless burst) usually beats either pure option.

**3. vLLM server flags that encode the above** (flag names stable as of 2026; check `vllm serve --help` on your version):
```bash
vllm serve meta-llama/Llama-3.3-70B-Instruct \
  --max-model-len 16384              # what you support, not what the model allows
  --gpu-memory-utilization 0.90 \
  --max-num-seqs 128 \               # batch ceiling: raise until SLO edge, watch ITL
  --enable-lora --max-loras 8 \      # multi-LoRA on shared base (if applicable)
  --tensor-parallel-size 2
# Prefix caching and chunked prefill are on by default in the V1 engine (as of 2026).
# Autoscale on vllm:num_requests_waiting; alert on KV-cache usage > 0.90 and preemptions > 0.
```

## Verification / self-check

Before presenting a serving design or diagnosis, confirm:
- [ ] The cost comparison uses the *real* request shape (in:out token ratio), *measured or honestly estimated* duty cycle, and prices checked this quarter — every number dated, nothing recalled from training data.
- [ ] SLO stated first (TTFT, inter-token, availability), and the batching/scaling design is derived from it — not "maximize utilization" in a vacuum.
- [ ] The autoscaling signal is queue/concurrency/KV-based; scale-up threshold accounts for measured cold-start time; the thundering-herd path (N replicas booting at once) is analyzed.
- [ ] Streaming path tested through the full proxy chain; disconnect-abort verified by killing a client mid-stream; retry policy is idempotent with a retry budget.
- [ ] Long-input behavior load-tested (max context × concurrency), gateway-level input caps in place, max_tokens bounded per endpoint.
- [ ] Rollout has an offline eval gate and an entity-randomized canary; rollback keeps the incumbent warm.
- [ ] Complexity is proportionate: every piece of the stack (k8s, disaggregation, KV-aware routing, MIG) is justified by a number, not by fashion.
Stopping rule: the design is done when the SLO is met at peak with ~20–30% headroom, the cost model beats the best alternative you rejected (and you can show the arithmetic), and the failure drills — cold start, spike, long prompt, mid-stream disconnect, bad model rollback — have each been run once. Optimization beyond that is speculative; revisit when traffic shape, model size, or prices change materially.
